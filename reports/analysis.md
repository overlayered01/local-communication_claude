- 첫 토큰 지연은 모델 크기와 무관하게 280~330ms로 사실상 동일합니다. Ollama의 프롬프트 처리 오버헤드가 지배적이라, LLM 선택은 지연이 아니라 품질과 VRAM으로 결정하면 됩니다.
- EXAONE은 한국어 문법 5.00으로 가장 정확하지만 답이 길어(간결성 4.21, E2E 오디오 12초) 음성 대화에 불리합니다. 반말 맥락에서 존댓말로 전환하는 경우도 관찰되었습니다.
- Qwen3 8B는 "mong이" 같은 로마자 혼입, Qwen3 14B는 "잔반을 주고" 같은 어휘 오류가 한 번씩 관찰되었습니다. 샘플이 적어 빈도 판단은 추가 측정이 필요합니다.
- Gemma3 12B와 Qwen3 8B는 이모지를 자주 붙입니다. 파이프라인이 TTS 전에 제거하지만, 시스템 프롬프트에 금지 문구를 넣는 것이 근본 해결입니다.
- 채점 모델이 Qwen3 14B라 자기 선호 편향 가능성이 있습니다. 14B 자신이 4위여서 편향이 크지는 않아 보이나, 더 큰 외부 모델로 재채점하는 것을 권합니다. 점수 분포가 4.2~5.0으로 압축되어 변별력이 낮습니다. 루브릭을 더 엄격하게 하거나 쌍대 비교(pairwise)로 바꾸는 것을 검토합니다.

# 2차: 첫 음성 지연의 원인 분석 (2026-09-17)

## 한 것

`pipeline/streaming.py`를 LLM 생산자 태스크와 순서 보장 오디오 드레이너 태스크가 하나의 이벤트 큐로 합류하는 구조로 바꿨습니다. 오디오는 합성이 끝나는 즉시(앞 문장이 모두 나갔다면) 나가며, LLM 델타 도착을 기다리지 않습니다. 가짜 LLM/TTS로 이를 검증하는 테스트 3개를 추가했습니다(`tests/test_streaming.py`). 오류 전파와 태스크 정리도 함께 정리했습니다.

같은 5개 조합을 `--label v2`로 다시 측정해 이전 행과 나란히 비교했습니다(`summary.md`의 `@v2` 행).

## 결과: 첫 음성 지연은 줄지 않았다

| 조합 | 첫 문장→첫 음성 간격 (이전) | 간격 (v2) |
|---|---|---|
| qwen3 8B + supertonic GPU | 460 | 528 |
| qwen3 8B + melotts | 256 | 275 |
| exaone + supertonic GPU | 344 | 297 |
| gemma3 12B + supertonic GPU | 450 | 495 |
| qwen3 14B + supertonic GPU | 481 | 502 |

중앙값 기준 ms. 샘플 8개, 출력 텍스트가 매번 달라(temperature 0.7) ±50ms 정도는 잡음입니다.

가설이 틀렸습니다. 이전 구조에서도 Ollama는 델타를 수 ms 간격으로 보내므로 "다음 델타까지 대기"는 실제로는 거의 0이었습니다.

## 진짜 원인: 같은 GPU에서 LLM 디코딩과 TTS가 경합

TTS를 단독으로 돌릴 때와 Qwen3 8B가 디코딩 중일 때를 같은 문장 5개로 비교했습니다(`scratchpad/contention.py`, 중앙값).

| TTS | 단독 | LLM 디코딩 중 | 배율 |
|---|---|---|---|
| supertonic GPU | 223 ms | 457 ms | 2.0x |
| melotts KR | 228 ms | 359 ms | 1.6x |

첫 문장이 TTS로 넘어가는 시점(~370ms)에 LLM은 아직 나머지 문장을 생성하고 있으므로, 첫 문장 합성은 항상 경합 상태에서 실행됩니다. 간격 300~500ms가 이것으로 설명됩니다. TTS 단독 벤치의 195ms는 파이프라인 안에서는 달성되지 않는 수치입니다.

## 선택지

1. **현 상태 수용.** 첫 음성 600~900ms는 이미 1초 안이며, 문장 단위 스트리밍의 구조적 한계입니다. 제품 요구 지연이 1초면 추가 작업이 필요 없습니다.
2. **첫 문장 우선 모드.** 첫 문장 종결 부호에서 LLM 생성을 멈추고(stop 시퀀스), 합성이 끝난 뒤 이어서 생성합니다. Ollama의 KV 캐시 재사용으로 재시작 비용은 작을 것으로 예상되나, 응답 이어쓰기의 품질과 구현 복잡도를 검증해야 합니다. 기대 효과는 첫 음성 약 250ms 단축.
3. **TTS를 GPU 밖으로.** Supertonic CPU는 2초로 불가. MeloTTS CPU 경로는 미측정이며 후보가 될 수 있습니다.
4. **더 작은 LLM 또는 더 낮은 디코딩 부하.** GPU 경합은 LLM 쪽 부하에 비례하므로 8B 이하 모델이 유리합니다. 이번 데이터에서도 8B 조합이 12B/14B보다 간격이 짧습니다.

## 그 외 관찰

- 파이프라인 변경은 유지합니다. 지연 개선은 없지만 LLM이 일시 정지하거나 실패할 때 오디오가 막히지 않고, 오류가 소비자에게 전파되며, 테스트로 보호됩니다.
- Qwen3 14B는 v2에서 llm_done이 742→949ms로 늘었는데, 생성된 답이 더 길었기 때문입니다(audio_sec 7.9→10.6). 모델 간 비교 시 답 길이 차이를 보정해야 합니다.

## 관찰

- **정확도는 Whisper 계열이 압도적**입니다. turbo fp16/int8은 32클립 모두 CER 0. int8은 VRAM을 1GB 줄이고 지연 손실이 없어 **whisper_turbo_int8이 GPU 기준 1차 추천**입니다.
- **CPU 후보**: zipformer_ko가 66ms로 가장 빠르고 CER 2.2%, SenseVoice가 87ms에 3.2%입니다. 둘의 오류는 대부분 영어 약어("API", "REST")를 소리 나는 대로 적는 것("아르에스티", "에이아")과 띄어쓰기 누락으로, 순수 한국어 발화에서는 거의 정확합니다. LLM과 GPU를 나눠 쓰지 않는다는 점(2차 분석의 경합 문제)에서 **zipformer_ko가 CPU 기준 추천**입니다.
- **스트리밍**이 필요하면 zipformer_ko_streaming(CER 2.8%)이 유일한 실용 후보입니다. Vosk는 지연 2.4초, CER 16%로 탈락입니다. 이 벤치는 클립 전체를 한 번에 넣은 것이라 스트리밍의 실제 이점(말하는 중 부분 결과, 종료 감지)은 측정하지 않았습니다. 웹 테스터에 부분 결과 표시를 붙여 별도로 봐야 합니다.
- **한국어 파인튠 turbo(whisper_turbo_ko)는 원본보다 나쁩니다**(CER 8.7%). 문장 중간에서 끊거나("혹시 점심은 드셨어요" 후 절단) 영어 약어를 잘못 전사합니다. 특정 데이터셋(Zeroth 등)에 과적합된 것으로 보이며, 이 후보는 제외합니다.
- whisper_small_cpu는 정확하지만 1초가 걸려 대화용으로는 느립니다. CPU에서 Whisper를 쓰려면 tiny/base급이어야 하고, 그 정확도는 zipformer/SenseVoice에 못 미칠 것입니다.
- 모든 엔진이 어려워한 클립은 영어 혼용 문장(english_mix)입니다. 제품에서 영어 약어가 잦다면 STT 뒤에 후처리 사전(아르에스티→REST)이나 LLM 측 교정 프롬프트가 필요합니다.

## 환경 이슈 (README 표에도 반영)

- Windows 11 System32의 구버전 onnxruntime.dll이 sherpa-onnx 확장 모듈에 잡혀 크래시 → pip onnxruntime DLL을 먼저 로드하는 헬퍼로 해결.
- SenseVoice 2025-09-09 릴리스가 sherpa-onnx 1.13.8에서 깨진 텍스트 출력 → 2024-07-17 릴리스 사용.
- **torch가 CPU 빌드로 조용히 교체됨**: torch가 MeloTTS의 간접 의존성이어서 `[tool.uv.sources]`의 cu128 인덱스 지정이 적용되지 않았고, 처음부터 lock에는 PyPI CPU torch가 있었습니다(venv에만 수동 설치한 cu128이 남아 있었음). `uv sync`를 하자 CPU 빌드로 바뀌어 faster-whisper의 cuBLAS 로딩이 실패했습니다. torch/torchaudio를 `gpu` extra로 직접 의존성에 넣어 해결. **재현성에 영향을 주는 문제였으므로 새 환경에서는 반드시 `--extra gpu`를 포함해야 합니다.**

# 0단계: 엔진별 세부 파라미터 조정 (2026-09-17)

- 모든 어댑터(LLM 3, TTS 5, STT 3)가 `PARAMS`로 조정 가능한 파라미터를 선언합니다. 런타임 파라미터(temperature, voice, beam_size…)는 살아 있는 엔진에 즉시 적용되고, 재로드 파라미터(model, device, compute_type…)는 엔진을 다시 올립니다.
- CLI: `--set k=v`(반복), `--sweep k=v1,v2`, E2E는 `--set-llm/--set-tts/--set-pipeline`. `llmcomm params <kind> <option>`으로 목록 확인.
- 결과 행 이름에 오버라이드가 붙고(`ollama_qwen3_8b{temperature=0.3}`), `meta.params`에 적용된 전체 값이 기록됩니다.
- 웹 테스터 "세부 옵션" 패널이 스키마로 폼을 자동 생성하고, 요청마다 오버라이드를 보내며, 프리셋 저장으로 YAML을 만듭니다. 이전 요청의 오버라이드가 다음 요청에 남지 않도록 프리셋 값으로 복원한 뒤 적용합니다.
- 이 기반 위에 1단계(시스템 프롬프트 옵션화)와 2단계(RAG)를 얹습니다.

# 1단계: 시스템 프롬프트 옵션 비교 (2026-09-17)

`configs/prompt/` 6개 프리셋 중 4개(default, voice_banmal, voice_jondae, persona_friend)를 LLM 5종 × korean_chat 8문항으로 측정했습니다.
규칙 지표는 LLM judge 없이 기계 채점: 문장 수, 이모지·마크다운 수, 존댓말/반말 문장 수, 규칙 위반 여부(`style_violations`).

## 관찰

- **이모지 문제는 프롬프트로 완전히 해결**됩니다. default에서 모델당 3~8개 나오던 이모지가 규칙을 넣은 모든 프롬프트에서 0(EXAONE만 1)이 됐습니다. 파이프라인의 TTS 전 제거 로직은 안전망으로만 남습니다.
- **말투 고정은 대부분 지켜집니다.** 존댓말/반말 문장 수가 거의 한쪽으로 몰립니다. 예외는 EXAONE(반말 요구에 존댓말 1회)과 Llama 3.1(양쪽 각 1회)입니다. default 프롬프트에서는 모델마다 말투가 제멋대로였습니다(qwen3 8B 5/16, gemma 7/13).
- **"2문장 이내"는 모델별 순응도가 크게 다릅니다.** Qwen3 계열은 거의 지키고, Gemma3 12B와 EXAONE은 존댓말 프롬프트에서 3문장 이상으로 늘어나 위반율 60~75%입니다. 음성 대화의 답 길이(=오디오 길이)를 통제하려면 Qwen3가 유리합니다. 이는 1차 judge의 간결성 점수(qwen3 8B 4.58, gemma 4.83, exaone 4.21)와 부분적으로만 일치하는데, judge는 "장황함"을, 규칙 지표는 "문장 수 상한"을 봅니다.
- **답 길이가 줄면 총 생성 시간도 줍니다.** qwen3 8B: default 461ms → voice_banmal 433ms, persona_friend 421ms. 오디오 길이 감소 효과는 E2E에서 더 크게 나타날 것입니다.
- few-shot이 있는 persona_friend는 qwen3 8B, gemma, llama에서 위반 0%로 규칙 문장만 있는 voice_banmal보다 순응도가 높았습니다. 예시가 규칙 서술보다 효과적입니다.
- default 행의 위반율은 규칙이 없어 0으로 표시되지만, 실제로는 이모지 20개, 말투 혼용이 있었습니다. 비교 시 지표의 의미 차이에 주의.

# 2단계: RAG 옵션 1차 비교 (2026-09-17)

LLM은 Qwen3 8B, 프롬프트는 voice_jondae 고정. 코퍼스 3종(제품 FAQ 12섹션/13청크, 사용자 기억 7청크, 페르소나 설정 8청크)에 대해
질문 12~15개(자료에 없는 질문 1개 포함)로 측정. 각 질문은 RAG 있음/없음 두 번 실행해 같은 표에 기록(`@rag=none:<corpus>`).

| RAG 옵션 | recall@k | 답 키워드 포함 | 검색 ms | 컨텍스트 글자 | 프롬프트 글자 | TTFT | 총 생성 |
|---|---|---|---|---|---|---|---|
| faq_bge_m3 (dense, k=3) | 1.00 | 1.00 | 19 | 313 | 635 | 312 | 544 |
| faq_bge_m3_hybrid (+BM25 RRF) | 1.00 | 0.93 | 16 | 357 | 680 | 315 | 572 |
| faq_bm25 (BM25만, CPU) | 1.00 | 0.93 | 0 | 357 | 680 | 314 | 551 |
| faq_bge_m3_k1 (k=1) | 1.00 | 0.87 | 16 | 112 | 427 | 298 | 534 |
| faq_qwen3_embed | 1.00 | 0.93 | 31 | 356 | 679 | **1066** | **2553** |
| faq_nomic (영어 중심) | 0.43 | 0.47 | 15 | 319 | 642 | 314 | 534 |
| memory_bge_m3 | 1.00 | 0.92 | 17 | 228 | 559 | 305 | 514 |

| (RAG 없음) persona_lore | - | 0.17 | 0 | 0 | 252 | 302 | 476 |

## 관찰

- **RAG 효과는 명확합니다.** 근거 없이 답하면 키워드 포함률 12~17%이고 전부 그럴듯한 환각입니다("보라색은 사랑과 감정을 상징하는 색"). bge-m3 검색을 붙이면 100%로 정답을 말합니다.
- **지연 비용은 거의 없습니다.** 검색 19ms, 프롬프트가 250→635자로 늘어도 TTFT는 304→312ms(+8ms). 음성 대화 예산 안에서 RAG는 공짜에 가깝습니다. 단, 코퍼스가 수십 청크 수준이라 top_k=3의 컨텍스트가 300자에 그친 덕입니다. 컨텍스트가 2천 자를 넘으면 다시 측정해야 합니다.
- **BM25만으로도 이 규모에서는 충분합니다.** 임베딩 없이 CPU에서 0ms, recall 1.0. kiwi 형태소 토큰이 한국어 어절 변화를 잘 흡수합니다. 코퍼스가 커지거나 표현이 달라지는 질문(유의어)에서 차이가 날 것이므로 더 큰 코퍼스로 재검증이 필요합니다.
- **임베딩 모델의 한국어 지원이 결정적**입니다. nomic-embed-text는 recall 0.43으로 절반을 놓쳤습니다. bge-m3가 기본 선택입니다.
- **qwen3-embedding은 검색 품질은 좋지만 LLM 턴을 3배 느리게 만들었습니다**(TTFT 1066ms). Ollama에 임베딩 모델과 대화 모델이 함께 올라가면서 모델 교체 또는 VRAM 압박이 생긴 것으로 추정됩니다. 원인 분리 전까지는 제외합니다. bge-m3는 같은 조건에서 영향이 없었습니다.
- **k=1은 위험합니다.** 컨텍스트가 너무 적어 자료에 없는 질문에 "네, 변경할 수 있습니다"라고 지어냈습니다. k=3 dense는 "변경할 수 없습니다"로 바르게 거절했습니다.
- **"자료에 없는 질문" 지표는 미완성**입니다. 키워드 규칙("모른/없")로는 "지원하지 않습니다"같은 올바른 거절을 잡지 못합니다. 이 항목은 judge로 채점해야 합니다.
- 페르소나 설정 RAG는 캐릭터가 1인칭으로 설정을 자연스럽게 말합니다("운전면허는 없어요. 대구에서 자랐고…"). 다만 근거에 없는 세부를 덧붙이는 경향이 보여 few-shot과 결합해 볼 가치가 있습니다.
